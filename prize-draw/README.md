# ZEP 경품 추첨 앱 — 외부 DB 없이 운영

유저가 맵 에디터의 **개발자 기능 → ZEP Script 상호작용 오브젝트**에 접촉하면 **로또 추첨 팝업**이 열리고, 공이 섞인 뒤 당첨 공·등수·경품명·당첨번호를 보여줍니다. 등수별 총수량과 하루 당첨 한도를 ZEP `App.storage`에 기록하는 **독립 사이드바 앱**입니다. 기존 코인·스탬프·위시리스트 앱과 별도로 설치합니다.

- [설치용 ZIP 다운로드](https://github.com/junho3789/ZEP/raw/refs/heads/main/prize-draw/zep-prize-draw.zip)
- [main.js 보기](https://github.com/junho3789/ZEP/blob/main/prize-draw/main.js)
- [main.js 원본 다운로드](https://raw.githubusercontent.com/junho3789/ZEP/main/prize-draw/main.js)

## 추첨 팝업

오브젝트 접촉 → 개인 팝업 열기 → 공 자동 혼합(약 3.6초) → 공 1개 배출 → 등수·경품명·당첨번호 표시 순서입니다. 추가 추첨 버튼 없이 자동으로 진행됩니다. 모바일 폭에 맞춰 화면이 줄어들며, 기기의 모션 감소 설정에서는 긴 연출을 생략합니다.

- 경품명은 `main.js` 상단 `prizeNames`에서 등수 id에 맞춰 바꿉니다. 기본은 `1등 경품` 같은 임시 명칭입니다. 실제 경품이 확정되면 `rank1: "실제 경품명"`처럼 입력하세요. 표시명 변경은 재고 설정 지문에 영향을 주지 않지만 이전 당첨 결과의 표시명도 현재 명칭을 따릅니다.
- 화면의 공은 연출용입니다. 실제 당첨 등수는 서버 스크립트가 재고/일일 한도 검증 후 결정하고 **저장 재조회 성공 후에만** 팝업으로 전송합니다. 화면의 공 개수는 잔여 재고를 의미하지 않습니다.
- 열린 팝업에 반복 접촉해도 새 추첨은 추가되지 않습니다. 닫기·이탈 후 재접촉하면 저장된 같은 당첨을 복구하며 경품을 추가 소모하지 않습니다. 팝업이 닫혀도 이미 시작한 추첨은 서버에서 완료될 수 있습니다.
- 로그인 필요·추첨 중지·당일 경품 소진·저장 오류는 팝업에서 안내합니다. 저장 오류를 가짜 당첨 연출로 대체하지 않습니다.
- 팝업을 닫으려면 ×, 확인했어요 버튼 또는 Escape를 사용합니다. 브라우저 메시지로 등수/추첨 요청을 임의 전송해도 경품을 배정하지 않습니다.
- 외부 이미지·폰트·라이브러리 요청 없이 HTML/CSS/Canvas만 사용합니다.

브라우저에서 `prize-draw.html?preview=1`을 열면 **샘플 2등 결과**로 연출을 볼 수 있습니다. 실제 ZEP 추첨이나 원장 저장을 하지 않는 미리보기이며, ZEP 안에서는 이 미리보기 경로로 당첨을 만들지 않습니다. 로컬 파일 열기가 제한된 브라우저는 해당 폴더에서 `python3 -m http.server 8000` 실행 후 `http://localhost:8000/prize-draw.html?preview=1`로 확인하세요.

[PC 화면 예시](https://github.com/junho3789/ZEP/blob/main/prize-draw/previews/desktop.jpg) · [모바일 화면 예시](https://github.com/junho3789/ZEP/blob/main/prize-draw/previews/mobile.jpg) — 커피 교환권은 화면 검증용 샘플이며 운영 기본값은 등수별 임시 경품명입니다.

## 이전 버전에서 업데이트

기존 `prize-draw` 앱의 ZIP을 이 버전으로 업데이트하되 `eventId`, `drawMapId`, `totalPrizes`, `ranks` 설정을 기존과 동일하게 유지하세요. 정상적인 기존 v1 당첨 기록은 삭제하지 않고 R1으로 이어받습니다. 기본 `interactionMode: "editor"`는 아래 Number/Value 방식입니다. 이전 key 방식을 계속 쓰려면 `interactionMode: "key"`, 좌표 방식을 쓰려면 `interactionMode: "position"`을 명시하고 기존 `objectKey`/`objectPosition`을 유지하세요. 기존 앱의 Q/채팅/사이드바 추첨 입구는 오브젝트 참여 안내로 바뀝니다.

## 기본 배정 예시

| 등수 | 전체 수량 | 하루 최대 당첨 |
|---|---:|---:|
| 1등 | 6 | 2 |
| 2등 | 8 | 3 |
| 3등 | 36 | 10 |
| 4등 | 150 | 50 |
| 5등 | 800 | 200 |
| 합계 | 1,000 | 265 |

1·2등을 제외한 수량 및 일일 한도는 임시 예시입니다. 확정 후 코드 상단 `PRIZE_CONFIG`에서 수정하세요.

## 설치

1. ZIP을 내려받아 압축을 풉니다.
2. **운영 전** `drawMapId`를 실제 추첨 맵의 런타임 ID로 설정합니다. `https://zep.us/play/rbbq9p` 같은 단축 링크의 코드를 맵 ID로 추정하지 마세요. 먼저 미설정 상태의 앱을 설치한 뒤, 추첨할 맵에서 관리자 채팅 `!경품맵확인`을 입력합니다. 개인 메시지로 받은 `drawMapId: "실제값"`을 `main.js` 상단에 복사하고 ZIP을 다시 올려 같은 앱을 업데이트하세요. 미설정 상태에서는 맵 확인만 가능하며 추첨은 차단됩니다.
3. **맵 에디터 → 오브젝트설치 → 개발자 기능 → ZEP Script 상호작용**을 선택하여 경품 위치에 배치합니다. 오브젝트 설정에 **Number: `1001`**, **Value: `prize_draw`**를 입력하고 저장합니다. 코드 기본값 `interactionMode: "editor"`, `objectNumber: "1001"`, `objectValue: "prize_draw"`와 일치시킵니다. 이 모드에서는 key나 레이어/좌표 입력이 필요 없습니다. 이미지는 맵 에디터에서 선택하며 스크립트가 자동 배치하지 않습니다.
4. `eventId`, `totalPrizes`, `ranks`를 확정합니다. `totalPrizes`는 모든 등수의 `total` 합계와 같아야 합니다. 각 등수의 `dailyLimit`가 하루 상한이며, 0이면 해당 등수를 배정하지 않습니다.
5. 수정한 `main.js`와 **`prize-draw.html` 두 파일을 모두 ZIP 최상위**에 넣어 다시 압축합니다. HTML을 빠뜨리면 팝업을 열 수 없습니다. README와 tests는 앱 업로드에 필요하지 않습니다.
6. ZEP의 스크립트 앱 제작/업로드 기능에서 새 **사이드바 앱**을 만들고 ZIP을 올려 추첨 스페이스에 설치합니다. 기존 앱의 `main.js`를 교체하지 마세요.
7. **추첨 맵 하나, 실행 인스턴스 하나, 앱 설치 하나**로 운영합니다. 다른 맵에서는 추첨 요청을 거절합니다. 같은 맵을 여러 채널/서버 인스턴스로 분리하거나 동일 앱을 중복 실행하면 안 됩니다.
8. 별도 테스트 스페이스에서 로그인 계정 두 개와 관리자 계정으로 오브젝트 상호작용과 아래 명령을 점검한 후 운영하세요. 일반 유저의 채팅 `!추첨`, Q키, 사이드바 클릭은 경품을 배정하지 않습니다.

CLI로 설치 ZIP을 만들 때(압축을 푼 디렉터리에서):

```sh
python3 -c 'from zipfile import ZipFile; z=ZipFile("upload.zip","w"); z.write("main.js"); z.write("prize-draw.html"); z.close()'
```

## 단축 링크에서 맵 ID 확인

접속 링크는 `https://zep.us/play/rbbq9p`처럼 짧을 수 있습니다. URL을 분리해 내부 맵 ID를 얻는 방식은 사용하지 않습니다. 스크립트의 `App.mapHashID`를 직접 조회합니다.

1. `drawMapId`를 기본 미설정 값으로 두고 이 앱을 업로드·설치합니다.
2. 실제 추첨할 맵으로 이동한 뒤 관리자/소유자 계정으로 `!경품맵확인`을 입력합니다.
3. 개인 메시지에 표시된 `drawMapId: "..."`를 코드에 복사합니다. `spaceHashID`와 혼동하지 마세요.
4. 수정한 `main.js`와 `prize-draw.html`을 ZIP 최상위에 넣어 **같은 앱을 업데이트**합니다.
5. 맵 저장·앱 실행 후 오브젝트로 테스트합니다.

맵 확인 명령은 설정 전이나 추첨 점검 중에도 동작하며 스토리지·재고·당첨 기록을 변경하지 않습니다. 현재 맵을 자동으로 추첨 맵에 등록하지도 않습니다. 기존 운영 중인 앱은 현재 `drawMapId`를 그대로 유지하세요. 조회한 다른 맵 ID로 변경하면 기존 설정 지문과 달라져 원장 접근이 차단됩니다.

## 맵 에디터 입력값

| 설정 위치 | 입력값 |
|---|---|
| 오브젝트설치 → 개발자 기능 | ZEP Script 상호작용 |
| Number | `1001` |
| Value | `prize_draw` |
| 스크립트 `interactionMode` | `"editor"` (기본값) |
| 스크립트 `drawMapId` | 실제 추첨 맵 ID |

공식 [ZEP 스크립트 상호작용 오브젝트 가이드](https://docs-kr.zep.us/creator/reference/script-object-interaction)에 맞춰 `onObjectTouched`로 오브젝트를 받고, 상호작용 타입과 `obj.text`(Number), `obj.param1`(Value)를 모두 검사합니다. 따라서 **기본 모드는 해당 오브젝트에 접촉할 때 실행**됩니다. 기존 F 키의 key/좌표 모드와 구분하세요. 같은 값의 오브젝트를 여러 개 배치하면 동일한 재고와 계정별 당첨 기록을 공유합니다. 재접촉 시 이미 당첨된 계정에는 기존 결과를 안내합니다.

```javascript
interactionMode: "editor",
objectNumber: "1001",
objectValue: "prize_draw",
```

Number 또는 Value를 바꾸면 스크립트 설정도 같은 값으로 변경하세요. 일반 오브젝트, 다른 타입, 값이 다른 오브젝트는 추첨하지 않습니다. 기본 모드에서는 `objectKey`/`objectPosition`은 사용하지 않습니다. 설정이 적용되지 않으면 먼저 맵 저장과 앱 실행 여부, `drawMapId`, Number/Value 값을 확인하세요.

고급 옵션: 이전 F 상호작용 방식이 필요하면 `interactionMode: "key"`와 `objectKey`를 사용하거나, `interactionMode: "position"`과 `objectPosition: { layer: 3, x: 10, y: 10 }`을 사용합니다. 레이어는 일반 오브젝트 3, 상단 오브젝트 5이며 좌표 모드는 레이어와 x/y 모두 일치해야 합니다. 기본 개발자 오브젝트 설정에서는 이 옵션이 필요 없습니다.

## 사용

| 입력 | 동작 |
|---|---|
| 지정한 ZEP Script 상호작용 오브젝트에 접촉 | 개인 팝업 자동 추첨 → 공 배출 → 경품 결과 표시 |
| `!추첨` 또는 사이드바 앱 클릭 | 오브젝트 참여 방법 안내(추첨 안 함) |
| `!경품도움말` | 사용 안내 |
| `!경품맵확인` | 현재 런타임 맵/스페이스 ID 확인, 관리자 전용·설정 전 사용 가능 |
| `!경품현황` | 등수별 전체/오늘 당첨 수 조회, 관리자 전용 |
| `!당첨목록 1` | 10명씩 현재 회차 당첨 원장 조회, 관리자 전용(페이지 변경 가능) |
| `!경품중지` | 추첨을 중지하고 상태를 저장, 관리자 전용 |
| `!경품시작` | 추첨을 재개하고 상태를 저장, 관리자 전용 |
| `!경품초기화` | 중지 상태에서 60초 유효 확인 코드 발급, 관리자 전용 |
| `!경품초기화 확인코드` | 코드 확인 후 재고·일일 당첨 수·당첨 기록 초기화, 관리자 전용 |

당첨 결과와 참여 제한 안내는 해당 유저의 팝업에 표시합니다. 팝업을 닫은 뒤 결과가 확정되면 개인 채팅으로 안내하며, 다음 접촉 시 팝업에서 기존 당첨을 다시 확인할 수 있습니다. 관리자 명령 결과와 목록은 요청한 관리자에게 개인 메시지로 표시합니다. 관리자 권한은 ZEP `role >= 3000`(관리자/소유자)입니다. 원장에는 당첨번호·등수·한국시간 날짜·시각·계정 이메일 해시 및 운영 상태/초기화 메타데이터를 저장하고, 이메일 원문이나 닉네임은 저장하지 않습니다. 계정 해시는 공개 저장소에 업로드하지 마세요.

## 관리자 초기화 사용 예

```text
!경품중지
!경품현황
!당첨목록 1
!경품초기화
!경품초기화 <개인 메시지로 받은 코드>
!경품현황
!경품시작
```

`<...>` 대신 실제 발급된 코드를 입력합니다. 초기화는 **현재 회차의 당첨자 원장 전체를 삭제**하고, 전체 재고·당일 한도 사용량·계정별 중복 당첨 제한을 모두 새로 시작합니다. 설정 수량과 타 앱의 스토리지 키는 유지합니다. 초기화 전에 필요한 당첨 목록과 지급 기록을 별도로 보관하세요. 앱 내부에 과거 전체 원장 백업은 만들지 않으며, 최근 초기화 관리자 ID·시각·이전 당첨 건수만 남깁니다.

회차는 R1 → R2로 증가하고 당첨번호에 포함되어, 새 회차 번호와 이전 번호가 구별됩니다. 초기화 완료 후에도 추첨은 **중지 상태**입니다. `!경품시작`으로 재개해야 하며, 이전 당첨 계정도 새 회차에서는 다시 참여할 수 있습니다. 초기화를 같은 날 실행하면 일일 한도도 새로 시작하므로 그날의 실제 누적 지급은 원래 한도보다 많아질 수 있습니다.

코드는 발급받은 관리자만 60초 안에 한 번 사용할 수 있습니다. 코드 발급 뒤 원장/운영 상태가 변경되거나 앱을 재시작하면 다시 발급받아야 합니다. 확인 단계에서는 재고를 지우지 않습니다. 일반 회원·스태프·에디터에게는 조회를 포함한 관리자 명령 권한이 없습니다. 관리자 명령은 추첨 맵에서 입력하세요. 중지/시작/초기화도 추첨과 같은 큐에서 직렬 처리합니다. 중지 명령보다 먼저 들어간 추첨은 먼저 처리될 수 있습니다.

## 추첨 규칙

- 기본은 **꽝 없는 추첨**입니다. 참여 가능한 계정에 대해, 남은 전체 재고를 가중치로 등수를 무작위 선택합니다. 예를 들어 1등이 2회 당첨되면 그날 남은 추첨에서는 1등을 제외합니다. 고정 확률이나 시간대별 배분은 구현하지 않았습니다.
- 일일 한도는 **상한**입니다. 반드시 그 수만큼 당첨되거나 1,000개가 행사 종료까지 자동 소진된다는 뜻은 아닙니다. 참여자 수와 행사 일수가 충분해야 합니다. 한도는 다음 날로 누적되지 않으며, 남은 전체 재고는 유지됩니다.
- 한국시간(UTC+9) 자정 기준입니다. 날짜별 원장에서 당일 사용량을 계산하므로 앱을 껐다 켜도 일일 한도가 초기화되지 않습니다.
- 초기화 회차당 로그인 계정별 **한 번 당첨**됩니다. 계정 키는 `player.emailHash`입니다. 게스트 또는 해시가 없는 계정은 참여할 수 없습니다. 재접속·다른 세션 ID로도 같은 계정의 기존 결과를 돌려줍니다. 여러 계정을 쓰는 동일인을 구별하는 기능은 없습니다.
- 오늘 모든 등수가 한도에 도달하면 당첨 이력을 쓰지 않고 내일 재참여를 안내합니다. 전체 경품 소진 시 종료를 안내합니다.
- 실제 쿠폰 발송이나 실물 지급은 하지 않습니다. 관리자는 당첨번호와 당첨 기록으로 별도 지급해야 합니다.

## 저장과 동시성

외부 DB/서버/HTTP 호출 없이 `App.getStorage(callback)` 안에서 읽고 `App.setStorage(string)`로 저장합니다. 원장 키는 `zepPrizeDrawV1`이며, 스토리지의 다른 최상위 키는 보존합니다. 전체/당일 사용량은 동일한 당첨 원장에서 계산해 별도 카운터 간 불일치를 피합니다.

한 실행 인스턴스 내 모든 요청은 큐에서 직렬 처리합니다. 같은 계정의 대기 요청은 합치고, 대기열이 100개를 넘으면 재시도를 안내합니다. 쓰기 후 재조회에서 원장이 일치한 경우에만 당첨 결과를 안내합니다. 저장 오류·응답 지연·원장 손상·설정 불일치 시 자동 재추첨이나 초기화 대신 해당 인스턴스의 추첨을 중지합니다. 결과가 불분명하면 `!당첨목록`으로 먼저 확인하세요. 단순 재시도는 같은 계정의 이미 저장된 당첨을 새로 배정하지 않습니다.

**운영 제약:** 공식 저장 API 문서에는 원자적 compare-and-swap, 분산 잠금, 영구 저장 완료 확인 기능이 명시되어 있지 않습니다. 따라서 재조회와 로컬 큐만으로 여러 맵/채널/인스턴스의 동시 추첨이나 저장 장애 시의 exactly-once를 보장할 수 없습니다. `drawMapId`는 다른 맵을 차단하지만, 같은 맵의 중복 인스턴스는 감지하지 못합니다. 반드시 단일 실행 인스턴스로 운영해야 하며, ZEP가 이를 제공하는지 확인할 수 없는 환경에서는 엄격한 재고 보장을 전제로 사용하지 마세요. 여러 실행 인스턴스 지원은 원자적 저장 기능 또는 외부 트랜잭션 저장소가 필요합니다.

서버 이전 이벤트가 제공되는 환경에서는 이전 시작 시 새 요청을 중지합니다. 이전으로 생기는 실행 중첩까지 원자적으로 제어할 수는 없습니다. 중단된 요청은 원장 확인 후 재시도해야 합니다. 원장 재조회는 ZEP 내부 동기화 확인이며 저장소 자체 장애/삭제/롤백에 대한 영구 보장을 추가하지는 않습니다.

`maxStorageBytes: 200000`은 이 앱이 적용한 자체 안전 한도입니다. ZEP의 공식 저장 한도를 의미하지 않습니다. 실제 계정의 스토리지 용량과 약 1,000건 원장 저장 가능 여부를 운영 전에 확인하세요. 용량 초과 시 새 당첨 기록을 쓰기 전에 중지합니다.

## 수량 변경·새 이벤트·장애 대응

- **수량 논의 중:** 첫 추첨 또는 관리자 상태 저장 전에 `totalPrizes`와 각 등수 `total`, `dailyLimit`를 자유롭게 수정하세요. 설정 합계를 검증합니다.
- **첫 추첨/상태 저장 이후:** 설정 지문과 원장을 비교하므로 수량·등수명·일일 한도·이벤트·맵 ID를 바꾸면 추첨이 중지됩니다. 기존 설정으로 되돌려 같은 원장을 유지하세요. 채팅 초기화는 **현재 설정의 원장이 정상인 경우에만** 동작합니다. 설정 불일치나 손상된 원장을 강제로 덮어쓰는 복구 명령은 제공하지 않습니다.
- **같은 설정으로 다시 운영:** 당첨 원장을 별도 보관하고 위 관리자 초기화 절차로 새 회차를 시작하세요.
- **수량/일일 한도까지 바꾸는 다음 행사:** 기존 앱과 원장을 보관하고, 새 앱을 만들어 새 `eventId`와 새 스토리지로 설치하세요. 현재 원장이 있는 앱에서 `eventId`나 설정만 바꾸면 초기화를 포함한 원장 접근을 차단합니다.
- **점검 메시지 발생:** 참여를 중지하고 원장과 설정, 실제 지급 기록을 대조한 후 원인을 해결하세요. 오류 상태는 런타임에 유지되므로 원인을 해결한 뒤 앱을 재시작해야 합니다. 저장소를 지워 복구하면 기존 당첨 제한과 재고가 사라집니다.

이는 ZEP API 모형을 사용한 자동 테스트입니다. 별도로 Playwright/Chromium에서 PC·모바일 화면, 연출 전 결과 비노출, 결과 표시, 중복 결과 메시지 무시, 안내 화면, 기존 당첨 표시, 모션 감소, HTML 문자열 안전 표시를 검증했습니다. 브라우저 테스트는 개발용 의존성이 필요하며 설치 ZIP에는 포함하지 않습니다.

```sh
npm install --no-save playwright
npx playwright install chromium
node tests/widget.test.cjs
```
